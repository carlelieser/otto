# The projection fold is pure, provenance is its own table, and the writer persists only what a batch touched

---
Status: accepted
---

ADR-0005 settled that projections are derived and rebuildable, and ADD §7 settled that every field names the event that last set it. Building both surfaced four decisions those two do not determine.

**The fold is a pure function in `domain/`, and the I/O is `application/`'s.** `project-entity.ts` takes a state and an event and returns the next state; it opens no database and reads no clock. [`qa.md`](../qa.md) §7.1 calls the rebuild property the load-bearing test of the entire projection design — for any log, dropping every projection and rebuilding produces byte-identical state — and a fold with no I/O makes that a property over a function, run 200 times against arbitrary logs, rather than a test that needs a database per case.

The alternative was folding inside the SQLite adapter, which is where a projection usually ends up. It costs the property: the same test becomes a database round-trip per generated log, and a counterexample prints a file rather than a log. The property against the store still exists (`tests/projection/rebuild-store.property.test.ts`), because a deterministic fold says nothing about whether the tables round-trip it — but it is the second line of defence rather than the only one.

**Per-field provenance is its own table rather than more JSON on the entity row.** ADD §7 asks that every field name the event that last set it and, through that event, the Proposal, the Capture, the model and version, the confidence, and whether a human confirmed it. `projection_field_provenance` holds one row per (entity, field) with the event's provenance columns flattened, mirroring `events`.

Two reads, two shapes. The entity view is "a row and a handful of joins" and renders without provenance; asking where one field came from is a separate click. Folding six provenance columns per field into `projection_entities.fields` would make every list query carry them, and every entity write rewrite them as one JSON blob. The columns are duplicated from `events` rather than joined to on `event_id`, which is denormalisation and is the point — ADD §7's argument is that building the pointer during projection is cheap and reconstructing it later is not, and a join back to the log on every field is reconstruction with extra steps against the one table the read path is not supposed to touch.

**The writer persists only the entities a batch touched, and the fold reports which those are.** This is the one decision here that was made by measurement rather than by reasoning. The first implementation wrote every entity on every batch, which is simple and obviously correct. Against [`qa.md`](../qa.md) §8's corpus it produced a 29 s rebuild against a 215 ms baseline and a 1.3 s hundred-event catch-up against a 500 ms bar — two bars degrading together, which §8 names in advance as the signature of the projection model doing too much work per event.

So `KnowledgeState` carries a `touched` set the fold adds to as it writes. It is carried rather than diffed because the fold already knows what it touched and a diff would be a slower second derivation of a fact that was free. The set grows in place while the maps around it are copied — a deliberate exception to the module being free of mutation, because copying it per event reintroduces the quadratic cost it exists to remove. It is safe because the set is bookkeeping about the fold rather than knowledge: the worst an earlier state could observe is a longer list of ids to rewrite.

**Search is FTS5 populated by the projection worker, not by triggers on the source tables.** ADD §7 puts full-text search over Captures and entity fields. A trigger on `captures` would be less code and would tie the index to the write path, making it the one projection that cannot be rebuilt by replaying — which is the property the `projection_` prefix is a promise about. Entity text is maintained as the worker folds; Capture text is not in any event, so that index is rebuilt from the `captures` table, which is a projection of truth rather than of the log and rebuildable all the same.

## Consequences

- **Rebuild is 8.4 s and catch-up is 145 ms, both well above the spike's baseline and both inside their bars.** The spike's projection logic was a stand-in that wrote entity rows only; this projector also writes a provenance row per field and maintains an FTS index, which is roughly three writes per event where the spike did one. [`qa.md`](../qa.md) §8 predicted this shape and says to watch the baseline column rather than the bars, so these figures — not the spike's — are what the next slice compares against. `tests/baselines/projection-performance.json` records what would count as a regression.
- **Catch-up reads the whole projection back before folding.** A worker resuming mid-log cannot start from an empty state: a `SetMemberAdded` needs the members already in the set to union against, and an entity's version is a count of every event folded into it. The round-trip is what the partial-plus-catch-up property exercises, and `ProjectionStore.read` exists for it rather than for any read surface.
- **`serialiseKnowledge` defines what "byte-identical" means, and `rowid` is not part of it.** Two projections holding the same knowledge must compare equal even when their maps were filled in different orders, so every collection is sorted by key. The same distinction holds in SQL: the provenance table is delete-and-reinsert per entity write, so physical row order depends on which batch boundary a catch-up used. Comparing on `rowid` fails rebuilds that are correct.
- **A rebuild reindexes Captures, because `reset` empties that index and no event can refill it.** Capture text is in no event, so the Capture search index is built from the `captures` table rather than folded. The first implementation left it to a caller, which meant a rebuild silently destroyed Capture search — ADR-0005's routine operation taking out a read surface. `ProjectionStore.reindexCaptures` is on the port for that reason, and `rebuild` calls it.
- **`touched` means "not yet persisted", not "recently changed".** A projection resumed from a snapshot has just had its tables emptied, so everything restored has to be written; a state reporting nothing touched would be persisted as nothing at all. `markEverythingTouched` is the inverse of `markWritten` and exists for that one caller, which is what fixes the meaning of the field.
- **A snapshot's stored shape is not the comparison key.** `serialiseKnowledge` sorts and flattens for stable comparison and is never parsed back; `snapshot-state.ts` keeps the shapes whole so a snapshot can be read back. Merging them would force the comparison key to be a storage format, which is a constraint it does not need. A snapshot that will not deserialise is discarded and the rebuild proceeds from zero — derived and disposable, so a corrupt one costs a replay and never data.
- **A crash mid-rebuild is visible rather than silent.** `projection_position.is_rebuilding` is set before the first row is written and cleared after the last, so a read surface can tell "Otto does not know this" from "Otto has not finished remembering it" — which [`qa.md`](../qa.md) §7.1 requires and [`qa.md`](../qa.md) §9 asks the application to handle gracefully rather than erroring at the UI. Every read on `application/surface/` returns the checkpoint alongside the data for that reason.
- **A user's search text is escaped into FTS5 syntax, never passed through.** FTS5's query language treats `AND`, `OR`, `NOT`, `NEAR`, `*` and `:` as operators and an unbalanced quote as a syntax error that throws. Every token is quoted as a literal and embedded quotes doubled, so `Q3: OKRs` searches for what it says instead of failing, and `Sarah OR Globex` does not silently widen. Phrase search and prefix matching are features with their own syntax if they are ever wanted; getting them by accident is what this prevents.
- **`projection_redirects` is declared and unwritten.** Merge and split are Slice 8's, and the table is here because the slice that builds the projection machinery is the honest place for it. Nothing reads it yet.
- **The snapshot mechanism is wired with its cadence at never.** [`runtime.md`](../runtime.md) §4.1 keeps the mechanism and sets the cadence to never, and this wires it into the worker rather than leaving it a module nothing calls — a mechanism with no caller is one that has quietly stopped working by the time it is needed. Snapshots hold the canonical serialised form, since a `SnapshotStore` may write to disk and `Map` does not survive JSON.
