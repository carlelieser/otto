# Confidence combines by multiplication; bootstrap constrains auto-apply; minimal merge ships in MVP

---
Status: accepted
---

ADR-0007 established that Confidence comes from the scorer and that `p(extraction)` and `p(resolution)` stay separate, "combined explicitly by triage." It did not say how. ADR-0006 required calibration sampling without setting a rate. Both gaps block the first implementable version of triage, and both are settled in [`triage.md`](../triage.md); this ADR records the decisions and the reasoning that is not obvious from the numbers.

**The two Confidences combine as a product.** `p(correct) = p(extraction) × p(resolution)`, with `p(extraction)` alone for creates and for field changes on an already-resolved entity. Multiplication assumes independence, which is false — a misread note also resolves badly — so the product systematically *underestimates*. That bias is deliberate and correct: it pushes marginal proposals toward review, which is the direction every other decision in the system already leans (ADR-0007, ADR-0009, PRD §4.4).

**Thresholds start at 0.90 and 0.50**, keyed by provider and model version (ADR-0008), and are explicitly initial values chosen to be wrong in the safe direction rather than measured ones. The asymmetry justifying a high bar: an unnecessary review costs seconds, a confidently wrong auto-apply costs a fact the user believes and never checks.

**Bootstrap mode constrains auto-apply until calibration has data.** Until 50 Corrections accumulate for the active provider and model version, `p(extraction)` is capped at 0.90, which by the product above means nothing requiring a resolution judgement can reach the auto-apply band. Only unambiguous creates and updates to already-resolved entities apply unattended. This exists because `p(extraction)` has no scorer behind it — it is the model's self-report, which ADR-0007 says cannot be trusted until checked against outcomes, and shipping without this cap would trust it in exactly the period when it is least examined. Fifty is ADR-0006's own threshold for an eval set rather than an anecdote.

**Sampling is 20% during bootstrap, 10% to 500 Corrections, 5% after**, with no user-facing off switch. An instrument that can be disabled will be disabled on the day it is most annoying, which is the day its data matters most.

**A minimal merge ships in the MVP**, reversing part of PRD §7.2. ADR-0009 established that duplicates are the expected steady-state outcome of resolution under uncertainty, and deferring all of merge would ship an MVP that has the failure mode and no remedy — a knowledge base that degrades with use. What ships is `EntitiesMerged` with transitive redirects over a user-confirmed pair, surfaced by duplicate detection as a Review queue entry. Field conflicts resolve by keeping the survivor's value and moving the loser's into `notes`, which is lossless and requires no interface. **Split stays deferred** as ADR-0009 has it: it genuinely needs the per-fact review affordance, and unlike merge it has no cheap lossless fallback.

## Considered Options

- **Take the minimum of the two Confidences** — defensible, and a weaker penalty than the product. Rejected because it discards the second signal entirely: two independent 0.9s should not score the same as a 0.9 and a 0.95.
- **A learned combination** — rejected: nothing to learn from on day one, and it forfeits the property that a human can read a disposition and say why.
- **Ship without bootstrap and tune thresholds after** — rejected: the tuning data is generated by the period the tuning is missing from.
- **Defer all of merge, per PRD §7.2** — rejected above.
- **Full merge and split in MVP** — rejected: split's review UI is real work (ADR-0009) and the duplicate problem does not require it.

## Consequences

- **Otto asks more questions in its first weeks than it will later**, by design. This is surfaced in the dashboard rather than left mysterious, since a user who does not know Otto is still calibrating will read the friction as the product being bad at its job.
- Switching providers or models re-enters bootstrap. Correct per ADR-0008 — a threshold measured against one model says nothing about another — and it makes model changes visibly costly, which is honest.
- **The `create` rule is the one place the application policy is more permissive than "creates are additive" implies**: an unambiguous create auto-applies, while a create made *after* rejecting candidates goes to review, because that is precisely the decision that manufactures duplicates.
- MVP scope grows by duplicate detection and minimal merge. Accepted as the cost of an MVP that stays usable past its first month.
