# Merge is a fold over the survivor, redirects resolve on read, and cardinality comes from the schema

---
Status: accepted
---

[ADR-0009](./0009-merge-and-split-semantics.md) settled that merge and split are events and that merged-away identities survive as transitive redirects. [ADR-0012](./0012-thresholds-bootstrap-and-minimal-merge.md) pulled a minimal merge into the MVP and left split deferred. Building that merge surfaced four decisions neither ADR determines.

**The survivor is the Command's aggregate and only the loser is in the payload.** `MergeEntities` targets the identity that survives and names the merged-away one in `MergeEntitiesPayload`. The alternative — both ids in the payload against some third aggregate — leaves the target free to be either one, so two merges of the same pair in opposite directions would both pass the executor's version check and both apply. Making the survivor the aggregate also makes a merge check a version like any other Command: a merge computed against a Sarah who changed while the user was deciding is refused rather than applied blindly.

**Redirects resolve on read, not at merge time.** The two places a merged-away id is still encountered are both reads: a proposal queued before the merge and approved a week after, and provenance display for an event whose target is, immutably, the old id. Both are resolved at the moment they are read — `EntityViewStore.resolveId` for the view, and the same call inside `ProposalAdjudication` for an entry the user answers.

The alternative is a sweep at merge time, rewriting every pending queue entry that names the loser. It costs the property ADR-0009 is built around: the merge would have to touch the review queue, and it would have to touch it again for each merge in a chain. Resolving on read means a chain of any length costs one walk at the moment someone asks, and a merge touches neither the queue nor the log. Both walkers are bounded — the fold's by the size of the redirect map, the store's by a constant — so a cycle from a corrupt row terminates rather than hanging every read of that id. The fold cannot produce one, since a merged-away id is gone and nothing can merge it again, but the store also reads redirects from a table.

**A merge is always restamped at adjudication, and so is any Command whose target moved.** The executor's version check exists to catch a stale *inference* — a Proposal whose target changed while it waited (`add.md` §5.6). A suspected duplicate is not one: it is a pair of ids detected by comparing the entity table against itself, and the pair does not stop being a duplicate because someone set a field on one side. A Command retargeted through a redirect is in the same position, since the version it carries is the merged-away entity's and means nothing about the survivor. Both are restamped against the target's current version, which is the argument `currentVersionOf` already makes for corrections arriving for a third case.

**Field cardinality at merge time is read from the schema.** The survivor's value is kept and the loser's moves into `notes` (`triage.md` §5), which needs to know whether a field replaces or accumulates. Counting the survivor's values answers this correctly except for a `set` field holding exactly one member — which is the common case for `aliases`, and getting it wrong there pushes a merged alias into `notes`, so the merged-away Sarah's alias stops finding the surviving one. `entity-schema.ts` is where cardinality is declared, and `domain/knowledge/` may import its sibling under `domain/`, so the rule asks rather than infers.

## Consequences

- **`KnowledgeState` carries a `redirects` map and `TouchedEntities` a `merged` set.** The map holds one hop per entry rather than a resolved destination, because that is what the log says: a later merge of the survivor adds its own entry, where storing the final answer would mean rewriting every earlier entry on each merge — a projection editing what it already wrote. `resolveRedirect` walks it.
- **The store applies merges after entity writes within a batch, and the order is load-bearing.** A batch holding both an entity's creation and its merging away touches it twice. Writing the rows and then removing them leaves the projection saying what the log says; the reverse order deletes and then re-inserts, which is a merged-away entity reappearing in every list view — visible only for logs where a merge lands in the same batch as its loser's last change. The arbitrary log generator emits merges, so the existing incremental-equals-rebuild property covers it.
- **A merge writes `notes` that no earlier event set, so `notes` points at the merge event.** This is the one field a merge can create rather than move. Pointing it anywhere else would attribute a line to an event that never said it; leaving it unpointed breaks the property `qa.md` §7.5 states over every field. The property found this — with merges in the generator, it shrank to two Persons with different names merged together — which is the case a hand-written test would not have included.
- **A merged-away entity's aliases, search text, and provenance rows are deleted with it.** An alias left behind keeps returning the merged-away entity as a candidate for resolution, which is the duplicate the merge just resolved arriving back through the door candidate generation reads.
- **Duplicate detection has no vector source, unlike candidate generation.** Nearest-neighbour over every pair is quadratic in embeddings rather than in names, and the two name sources are the high-precision ones. Losing the third costs recall on paraphrase, which for duplicates means a pair surfaces the next time either entity is renamed rather than never.
- **The duplicate floor is 0.85, tighter than candidate generation's 0.7.** That floor feeds a scorer that discriminates afterwards, so a loose one costs one comparison. This feeds the review queue directly, so a loose floor costs the user an entry — and a queue with false duplicates in it is one they stop reading.
- **Detected duplicates bypass triage, and that is what keeps merge from auto-applying.** Triage's answer is already fixed: the application policy's `merge` row is `needs_review` at any confidence, and the policy is asked about a kind of change rather than a number. Entries are written at `needs_review` directly. Running them through a threshold would create a path on which a very confident merge could apply unattended, which is what ADR-0007 forbids — and `DuplicateDetection` is wired to no executor at all, so the guarantee is structural rather than remembered.
- **A duplicate's Proposal id is derived from the pair alone**, with no Capture, no similarity, and no clock in the hash. The sweep runs repeatedly over a table that mostly does not change, and an id carrying any of those would make every run a fresh queue entry for a question the user has already been asked. Its `captureId` is its own id, because no note produced it and pointing at an unrelated Capture would put a claim in the provenance trail that never mentioned either entity.
- **Split remains absent, and `tests/inference/command-seam.test.ts` is what says so.** That test greps the source for a split Command, event, or handler, which means prose in this repository must describe the deferral without naming those identifiers.
